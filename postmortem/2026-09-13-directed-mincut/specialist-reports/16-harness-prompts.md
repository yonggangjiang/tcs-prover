## 4. Continuation and compaction prompts

As established in §0(a), the text that actually continued each turn was the `goal` objective ("Resolve the exact statement in INITIAL_PROMPT.md ... Follow its instructions and maintain the research records it defines"), plus the Codex runtime's periodic status-update requests (THINK "Sending periodic status update" 15:07:11, "Noting repeated summary request" 16:01:32). The compaction prompt (yaml 166–169) says "Read INITIAL_PROMPT.md now ... Recover the relevant saved context using its memory layout, preserve the records, and continue the same goal." Both texts (i) name only the records, never the plan or the missing step; (ii) say "continue the same goal", which the model read as "continue the same node" (after every one of the nine compactions the root resumed the node it had been writing; e.g. 18:31–18:36 closure splits, 19:09–19:12 hierarchy deletion costs, 21:16–21:19 A054); (iii) contain no stop rule, so a turn's "unresolved" summary is immediately followed by the same route. Assessment: they do not cause depth-first drift by themselves, but they guarantee it is never interrupted, and "maintain the research records" is the only concrete verb, which is why re-anchoring turned into index checking.

Replacement continuation text (to be placed in `goal` and also actually sent by the runner at each turn start):

```
Continue the same statement. Before touching any node file: (1) reread the STATEMENT and the PLAN section at the top of APPROACHES/index.md; (2) rewrite the PLAN from scratch in your own words without looking at the old one, then diff it against the old one and keep the better of each line; (3) name the single MISSING step and list the formulations already tried for it and why each failed; (4) pick the cheapest untried formulation (in this order: reuse an existence theorem as a black box, one flow/circulation plus rounding, iterative averaging or a Markov chain on the object, recursion, and only last a new data structure or optimiser) and spend this turn on it. Do not re-verify the index, links or old lemmas unless a lemma you are about to use is in doubt. End the turn by pasting the updated PLAN (at most 25 lines). Do not report counts of nodes or lemmas.
```

Replacement compaction text:

```
Context was compacted. Read INITIAL_PROMPT.md, then only the PLAN section of APPROACHES/index.md and the one node you were writing. Do not check the index, links or file structure now. Restate in two lines the missing step and what the current node contributes to it; if you cannot state the contribution, mark the node BLOCKED and return to the PLAN.
```

## 5. Proposed revised author prompt (full text) and lifecycle prompts

Design: keep INITIAL_PROMPT.md, APPROACHES/index.md + A###.md, PROVED.md, AUDITS/ unchanged in role; add one mandatory PLAN block at the top of index.md; replace per-node self-containment with links; add branch budgets, formulation ladder, existence-first rule, literature rule, negative-result cap, and a turn-end contract. Status vocabulary is kept (ACTIVE/BLOCKED/CLOSED/RESOLVED) but RESOLVED is split by a required "Closes the missing step: yes/no" line so the index can compute real progress.

```
Resolve the exact statement below with a complete, rigorous proof or algorithm. You are the author LLM; you create, read and update research records with file tools. Inspect the working directory first. For a new run, save this entire prompt verbatim as INITIAL_PROMPT.md, create APPROACHES/index.md with the heading "# Attempted approaches" and PROVED.md with "# Proved lemmas". Create files only if absent. For an existing run, read INITIAL_PROMPT.md and follow it.

FILE STRUCTURE (do not add files or directories):
1. INITIAL_PROMPT.md: this prompt and the statement. Read it at the start, after compaction and on resume. Never edit it.
2. APPROACHES/index.md: begins with a mandatory "## PLAN" section (format below), followed by the navigation table with one row per node: linked ID and title, parents, children, status, one-line result or remaining question. Update a row when its node changes; do not run link or reciprocity checks more than once per turn, and never as the first action after compaction.
3. APPROACHES/A###-short-title.md: one node per file (format below). An edge A -> B means B developed from A.
4. PROVED.md: important reusable lemmas with stable IDs L###, full statements and proofs, and links to the nodes they support or rule out. Withdraw a lemma if found wrong and record the correction in its node.
5. AUDITS/ and audit_history/: managed by the controller. Read new reports on resumption. Their strategic advice (which route to freeze, which to open) must be answered in the PLAN, one line per recommendation: adopted, or rejected with a reason.

PLAN (top of APPROACHES/index.md, at most 30 lines, rewritten from scratch at the start of every turn and after every compaction before any node file is opened):
- Target: the statement in one line.
- Best route: at most 6 steps; each marked PROVED (lemma ID), STANDARD (cite the black-box result and its exact interface) or MISSING.
- The missing step, stated as a precise theorem.
- Formulation ledger for the missing step: for each of (i) use an existence theorem as a black box, (ii) one flow/circulation/LP plus rounding, (iii) iterative averaging, contraction or a Markov chain on the object, (iv) recursion/divide-and-conquer, (v) reduction to O(polylog) calls of a known almost-linear primitive, (vi) a new data structure or optimiser: tried/untried, and if tried, the node ID and the one-line reason it failed.
- Budget: hours spent on the current route; the branch cap below.
- Audit responses (if any).
The turn-end message is the PLAN verbatim; do not report counts of nodes, lemmas, or index state.

STRATEGY RULES:
- Existence first. When an object is known or proved to exist (a packing, a polytope point, a feasible circulation), first design an algorithm that only CITES existence in its proof while COMPUTING a simpler object (a single flow, a single tree, a rounding, an average). Only after writing a paragraph showing why existence alone cannot suffice may you try to construct or maintain the object.
- Cheapest sufficient object. If only a weaker property of the object matters (e.g. marginals, expectations, one crossing), work with that property and look for a one-step improvement operator that can be iterated O(polylog) times.
- Formulation before machinery. Before building a data structure, a dynamic algorithm or an optimisation method, the ledger must show at least three cheaper formulations tried and closed with a written reason.
- Branch cap. A route (a top-level node and its descendants) gets at most 90 minutes or 3 descendant nodes, whichever comes first, before it must either close the missing step or be set BLOCKED with an Obstacles section. Tool nodes (nodes that build a component for a parent) must state in their opening which missing step they close; if they cannot, do not create them.
- Negative results about your own sub-proposals close that sub-proposal and go in the parent's Obstacles section; they become PROVED.md lemmas only if they rule out an entire ledger formulation. Two consecutive negative results on one route set the route BLOCKED.
- Literature. Use the literature only for black-box primitives with exact statements (e.g. almost-linear max-flow and min-cost flow, tree decompositions, rounding lemmas). Statements that the problem is open, hard or unsolved are not evidence and must not influence the plan, the tone, or the decision to deliver a progress report. Do not create nodes about the literature status.
- Progress is measured only by the PLAN: a step moving from MISSING to PROVED, or a ledger row moving from untried to tried with a reason.

NODE FORMAT (APPROACHES/A###-short-title.md):
# A### — Title
Parents: IDs or none.   Children: IDs or none.   Status: ACTIVE, BLOCKED, CLOSED, or RESOLVED.
Closes the missing step: yes / no / partially (say which step).
## Context and objective
At most 12 lines. Define only terms not in the statement or in PROVED.md; link to lemma IDs instead of restating them. State the objective and its exact role in the PLAN.
## Detailed work
Subsections, each opening with what it targets and how that relates to the objective. Proofs at full rigour; define every term on first use.
## Obstacles (BLOCKED only)
The obstacle, why it blocks, whether the route continues (child ID) or is abandoned (what replaces it, when to revisit).
## Conclusions (RESOLVED or CLOSED only)
What is proved or disproved, lemma IDs, and whether the PLAN's missing step changed.
ACTIVE = under development; BLOCKED = unresolved, obstacle recorded; CLOSED = an identified claim failed; RESOLVED = the node's objective is achieved (this does not by itself mean progress on the statement).

Return a complete, self-contained solution only when it resolves the exact statement and every claim is justified. A special case, a reduction to an unproved claim, or a progress report is not a solution.

STATEMENT:
[STATEMENT]
```
