Scope: read-only analysis. Files cited as `path:line`. "Measured" = computed from `transcript.jsonl` (2026-09-13 run, UTC); "estimate" = arithmetic on measured quantities under stated assumptions. Scratch scripts: `/private/tmp/claude-503/.../scratchpad/eff/cost_yj.py` (output in `cost_yj_out.txt`).

## 0. Measured cost profile of the run (what the levers act on)

Token accounting: raw `thread/tokenUsage/updated` events = 2,770, of which 512 are consecutive duplicates of the same `last` record (re-emitted at turn boundaries). Deduplicated: **2,258 provider calls; 267,945,496 input (258,896,896 cached, 9,048,600 uncached); 1,830,446 output (910,754 reasoning)** — this reconciles exactly with the verified totals in the task context.

Per thread (deduped calls / input / avg context): ROOT 665 / 79.1M / 118.9k; literature_status 361 / 47.0M / 130k; structural_approaches 301 / 35.0M / 116k; batch_supersets 268 / 31.0M / 116k; flow_reduction 289 / 30.9M / 107k; audit_cleanup 210 / 26.5M / 126k; approximation_proofs 164 / 18.4M / 112k. **Subagent threads = 1,593 calls and 188.9M input = 70% of all input tokens**; 125 results, so 12.7 calls and 1.51M input tokens per subagent result (measured).

Cost decomposition (ASSUMPTION A: GPT-5-class list ratios, uncached $1.25/M, cached $0.125/M, output $10/M; "fast" tier multiplier ignored): uncached $11.3 (18%), cached $32.4 (52%), output $18.3 (30%), total ≈ $62. ASSUMPTION B (cached only 50% off): cached share rises to 85%. Under either assumption the dominant cost is **re-sending the carried context on every call**: cached tokens = Σ_calls(context) = 2,258 × 118.7k avg. The levers are therefore, in order: number of calls, context size per call, output tokens, and only then uncached bytes.

Call composition (measured item counts; a response can carry several items, so shares are approximate): commandExecution 1,092 (375 root, 717 sub); inter-agent messages (`subAgentActivity` kind=interacted) 881 = 600 SUB→ROOT + 281 ROOT→SUB; agentMessage 338 of which **141 were standalone responses** (a full-context call whose only product was narration); webSearch 209; fileChange 79; contextCompaction 30; collab tool calls 21.

Context growth per compaction window (measured): ~60 calls/window; growth = uncached 9.05M + output 1.83M; replayed reasoning = 8% of growth (mean 11.5k of the 118.7k average context is accumulated reasoning within the window); tool/user input dominates (mean 131k accumulated per window). Post-compaction context restarts at 24–41k tokens; the next 10 calls after each of the 30 compactions add 23k–113k uncached (1.43M total = 16% of all uncached), i.e. the recovery ritual (INITIAL_PROMPT → index → AUDITS → nodes; `commands.txt` windows after 15:46:23, 16:32:10, 17:56:53, 18:31:14, 19:08:54, 19:42:14, 20:41:40, 21:16:44, 21:45:34).

Injected command output (measured): 10,545,007 bytes over 1,092 commands; SUB 7.17MB, ROOT 3.37MB. By content: node files 4.29MB (310 reads; A001 read 41×, A055 31×, A019 26×, A044 25×), AUDITS 1.17MB (44 reads; each full-batch `cat AUDITS/*.md` = 59,236 bytes, done by ROOT at 20:41:46, 21:16:57, 21:45:41 and by subagents), rg 0.85MB, python 0.69MB, PROVED 0.62MB (135 mentions; only 3 full cats, the rest `sed -n`/rg slices), INITIAL_PROMPT 0.61MB+ (**139 full `cat INITIAL_PROMPT.md`**, 155 mentions; 7.5KB file), index 0.11MB. 172 outputs >20KB carry 5.5MB (52% of bytes in 16% of commands).

Wall time: 15:06–22:06 = 7.0h, of which **62 min paused for two audit batches** (17:00–17:49, 19:49–20:13) while three CLIs read the workspace; auditor tokens are not recorded anywhere. The account's primary rate-limit window (10,080 min = 7 days) went from `usedPercent` 0 at 15:06:23 to 100 at 22:06:41 — the run consumed the whole weekly quota at ~46M input tokens per active hour and died with "usage limit" (control_events.txt 22:06:42).

## 1. Catalogue of xean mechanisms

Format: what (file:line) → cost controlled → how xean measures it → adaptation to tcs-prover → strength risk.

### A. Context construction (what a call sees)

**A1. Fresh turn from records, not transcript.** `docs/philosophy.md:11` "A new Explorer turn receives the original task, current guidance, every note's metadata, and the full supporting texts selected by the coordinator. It does not inherit the earlier turns' full reasoning transcripts." Implemented in `workflow.ts:249–265` (`notes: known.map(({ text, ...rest }) => rest)`, support = selected ∪ closure) and `roles.ts:202–216` (`explorerInput.notes` = `noteFields.omit({ text: true })`). → Controls context size per call and eliminates compaction entirely. → Measured by Pi's context estimate and `derivePiSpend` per call. → Adaptation: tcs-prover's author is one long-lived Codex thread; the analog is "turn = recover from records", i.e. every turn/compaction starts with one `records.py overview` (PLAN + index rows + lemma statements ≈ 10–25KB) and opens node sections on demand, instead of `cat` of whole files. Already drafted in the working-tree YAML (`CONTEXT DISCIPLINE`, `compaction`, `continuation` prompts) and `tools/records.py` (overview/node --section/lemma/grep/audits). Remaining: make the compaction ceiling low enough that the carried transcript is small (see E2). Risk: low (records were rigorous in this run; the postmortem shows unrecorded *reasoning* was the loss, which A1 addresses by forcing the PLAN write).

**A2. Metadata-only listing + selected full texts ("support").** `pi-roles.ts:209–216` Explorer prompt = task, notes (metadata), support texts, first note id, guidance; coordinator chooses `support` (`pi-roles.ts:250`, `roles.ts:288`). `docs/terms.md:54–55` support/closure. → context size. → Adaptation: the PLAN's BEST ROUTE lists lemma IDs; `records.py lemma L034` returns the statement only unless `--full`; the author reads proofs "only when about to use, extend, or verify that exact lemma" (already in the YAML). Runner-side helper remaining: none. Risk: low.

**A3. PASS explanations omitted from prompts; failures kept.** `pi-roles.ts:160–173` (`promptNote`: `verdict.verdict === "PASS" ? verdict : { ...verdict, report }`); `docs/role-runner.md:19`; `README.md(solve):21`. → uncached bytes and context size. → Adaptation: (i) verification records: a lemma's `Verified:` line carries who/when, never the verifier's reasoning; (ii) audits: `audit-digest.md` with per-node STOP/CONTINUE/REDIRECT lines and the three directions, full reports opened only to dispute a STOP (YAML already says this; `research_audit.yaml` diff adds the digest). Measured target: 1.17MB of AUDITS reads → ≈0.1MB. Risk: low.

**A4. Shared texts appear once; closure computed by one traversal.** `support.ts:8–31`; `workflow.ts:171–199` `verificationPrefix` (window counts shared texts once); tests `tests/efficiency.test.ts:69–116`. → uncached bytes. → Adaptation: prompt rule "read every needed file once, in one command; never re-cat a file already in context since the last compaction" plus `records.py` refusing to return the same node section twice per turn unless `--again` (runner helper: a per-turn read ledger in `/tmp`). Measured waste: INITIAL_PROMPT catted 139×, A001 41×. Risk: none.

**A5. Cache-friendly prompt ordering: stable prefix first, changing text last.** `docs/role-runner.md:25` "The model prompt places changing guidance after the notes and supporting proofs"; `pi-roles.ts:332–335` verifier calls "share the leading task, support, and note text so a provider can cache that prefix"; `pi-roles.ts:599–601` `cacheKey` from role+system; `SPEC.md:98` transport session ID for provider-side prompt caching. → cached vs uncached split. → Adaptation: tcs-prover already gets 98–99.5% cache hits (`control_events.txt` "Author cache usage" lines) because Codex appends; the remaining gain is small. Keep steers short and append-only; do not edit `INITIAL_PROMPT.md` mid-run (the run lost ~25 min re-formatting after two external edits; strategy rule 9 in the new YAML). Risk: none.

### B. Call structure (how many calls)

**B1. One logical call per role, one structured submission, no narration.** `pi-roles.ts:227–236` ("Call submit_notes exactly once"), `:262` coordinator, `:297` verifiers; `SPEC.md:88` `stopAfterToolResult: true` "finish after a successful tool batch without a redundant provider continuation"; `AGENTS.md:11` stable rules in system/developer instructions, changing directions as user messages, results in tool receipts. → number of calls. → Measured in xean by `inspect` call counts (`README(solve):69`). → Adaptation: (i) prompt rule "no interim commentary; the only text output of a turn is the PLAN paste at turn end" (141 standalone narration calls = 6% of calls ≈ 6% of cached cost); (ii) "batch your reads: one command per read plan" (the model already used 359 python heredocs; push the remaining 300 single-file cats into them). Risk: none (Codex's goal loop reads the final agentMessage; the PLAN paste is that message).

**B2. Roles communicate only through submissions; no agent-to-agent chat.** In xean the coordinator's `explorerGuidance` and the verifier's verdicts are the only inter-role messages, delivered at turn boundaries (`guidance.ts:90–141`, frozen once per turn). → number of calls on both sides. → Measured: tcs-prover had 881 inter-agent messages (600 SUB→ROOT status/progress updates, 281 ROOT→SUB) — each is a tool call, i.e. a full-context model response on the sender, and injected input on the receiver. → Adaptation: SUBAGENT POLICY (already drafted): one task, ≤2KB brief, report once and stop; add "do not send progress updates to the root; the root does not poll" and a runner counter that emits a diagnostic (and, above N interactions per subagent, a steer "finish and report") on `subAgentActivity kind=interacted`. Estimated saving: if chatter falls from 881 to ~150 calls at ~120k context, ≈ 85M cached tokens ≈ 33% of cached tokens ≈ 17% of cost (assumption A). Risk: low–medium (loses mid-task redirection; xean shows boundary-only guidance suffices, and the run's three most productive results came from open-ended subagents in the first 40 min, which a 4-response budget per spawn still allows).

**B3. Bounded continuation: response budget + context budget + reserve, then finalize.** `pi-roles.ts:186–189, 219–235` (`maxResponses` default 4, `contextBudgetTokens` default 400k, `continuationPrompt` "Keep trying, you can do it."); `SPEC.md:90` gate: reserve = model max output tokens, finalization takes precedence at the threshold; `docs/terms.md:30–32`. → calls per turn and context per call. → Measured via Pi's context estimator anchored to provider usage. → Adaptation for subagents: the root's brief states "at most K tool calls / one report"; runner enforces a per-subagent-thread call cap (count `thread/tokenUsage/updated` per subagent thread; at the cap send `subagent_compaction`-style steer "report now and stop"). For the author: see E2. Risk: low for verification/formatting chores (79+15 of 125 results), medium for exploration spawns (keep K larger, e.g. 40).

**B4. Empty submission ends the turn and forces a different approach.** `pi-roles.ts:205,231` (`emptyArgument: "notes"`), coordinator receives `emptySubmission: true` "Choose a different promising approach" (`:258–262`). → wasted continuation calls. → Adaptation: a subagent that reports "nothing new" ends; the root must record the failure in the parent's Obstacles and pick another ledger row (strategy rule 6) — a strength rule with a cost side effect (no repeated spawns on a dead route). Risk: none.

### C. Verification economy

**C1. Verify once, record it, never re-verify; settled calls are replayed, not rerun.** `AGENTS.md:29` "never reason again over what was already reasoned, so no result is verified or derived twice"; `workflow.ts:137–164` `settledCall`, `docs/role-runner.md:77,81,91` (resume makes only missing calls; the fold refuses mismatched prompt bytes rather than re-running); `pi-roles.ts:250,256` "Never ask the explorer to check, polish, or restate a verified note"; `README(solve):17`. → verification repeats. → Measured: xean counts calls per candidate. In tcs-prover, 79 of 125 subagent results were verification/check of sibling records (keyword classification of result texts; postmortem P3 says ~50 verification + ~47 writing), A001 read 41× and PROVED.md touched 135×, and 6 audits re-checked the same lemmas. → Adaptation: a verification ledger in PROVED.md (`Verified: L034 by <subagent/thread id> at <UTC>`; `records.py lemma` prints it; `records.py overview` shows unverified lemmas), prompt rule "verify a lemma once when promoted, by one fresh subagent given only the lemma text and the definitions it uses; never re-verify unless a dependent proof fails or an auditor STOPs it" (drafted in the YAML), and a runner check that a `fileChange` to PROVED.md adding a lemma without a `Verified:` line triggers one verification spawn request in the next continuation steer. Estimated saving: verification subagent work is ≈ 60% of the 189M subagent input by result share; halving repeats ≈ −55M input ≈ −20% of run input. Risk: low–medium (an unverified-wrong lemma stays longer; mitigated by audit STOP and by dependency failure).

**C2. Verification reads a bounded window; skip notes whose support failed; stop at first non-PASS.** `workflow.ts:171–199` (`window`, default 100,000 chars `pi-roles.ts:95–106`), `roles.ts:436–518` `judgedBy`, `docs/terms.md:59–61`. → tokens per verification and number of verifier calls. → Adaptation: a verification brief = lemma statement + proof + the definitions/lemmas it cites (records.py can assemble it: `lemma L034 --full` plus `lemma` for each cited ID), capped at ~100KB; nothing else. Measured contrast: xean verifier call ≈ 28k tokens input (100k chars / 3.6, assumption) × 2–5 calls; tcs-prover verification results cost 1.5M input tokens each (measured average across all subagent results). Risk: low (this is how xean verifies; postmortem found no false lemma).

**C3. Source verifier receives only notes with external premises, never support proofs; local PASS without a model call when there are no premises.** `pi-roles.ts:489–491, 546` ("Established support proofs have already been checked by correctness and are omitted"), `runLocalSource` path (`pi-roles.ts:~800–830`), `README(solve):15`. → calls and context. → Adaptation: literature checks get a one-paragraph brief (the exact cited statement and its use), not the workspace; a citation already checked (URL + quoted passage recorded in PROVED.md) is reused, as xean reuses inspected passages with provenance (`pi-roles.ts:283, 941–960`). Risk: low.

**C4. Reconstruction verifier (three calls per note, one never sees the text).** `pi-roles.ts:347–420`, `docs/role-runner.md:75`. → this *adds* cost for strength. → Adaptation only as an opt-in tier for lemmas on the BEST ROUTE (statement → fresh proof → compare); do not run it on tools. Risk: none (cost increase, strength gain).

### D. Web actions

**D1. Observed web-action cap with a cancel and "finish below the limit or return INCONCLUSIVE".** `pi-roles.ts:109` (`maxSourceWebActions` default 16), `:549` prompt, `source.ts:261–294` (counts distinct actions, sets `exhausted`, kills the process), `README(solve):38`. → web calls and injected results. → Measured: 209 searches in this run, 0.75MB results, 62 by literature_status alone, 25 on one paper (postmortem C3). → Adaptation: prompt cap (YAML now says 6 page fetches/hour) plus runner enforcement: count `webSearch` items per thread per hour and steer "stop searching; record INCONCLUSIVE" at the cap; auditors already get `-s read-only` and a timeout. Risk: low–medium (literature anchoring hurt this run; C3 in the postmortem).

**D2. Explorer and Pi verifiers get no web tools at all.** `pi-roles.ts:202, 297`. → Adaptation: partial — keep web only in a literature subagent with D1's cap; the author's own 28 searches are fine. Risk: low.

### E. Budgets and compaction

**E1. Turn cap and per-role model/reasoning profiles.** `pi-roles.ts:70–110` (`maxExplorerTurns` default 10; a profile per role with its own `reasoning` level); `docs/philosophy.md:15` "Compare success on held-out problems at comparable monetary cost". → output tokens (reasoning) and total spend. → Adaptation: Codex subagents inherit the parent's model/effort; this build exposes no `[agents.*]` model/effort keys (binary strings and the app-server JSON schema have none), but `TurnStartParams.effort` exists, so controller-initiated turns (repair, resume, audit-digest reading) can run at lower effort, and chores (index consistency, formatting, migration) can move to a `codex exec -c model_reasoning_effort=medium` structured node instead of the ultra author (the `audit_cleanup` thread alone was 26.5M input = 10% of the run, mostly record cleanup). Risk: medium if applied to mathematics; low for chores.

**E2. Context budget + reserve + finalization instead of unbounded growth then compaction.** `SPEC.md:90`; `README(solve):48` ("400,000 − 128,000 − 4,096 = 267,904 estimated context tokens" handoff threshold). → context per call. → Adaptation: the working tree already sets `model_auto_compact_token_limit` = 150,000 and a checkpoint steer at 120,000 (`workflow_runner.py` diff: `DEFAULT_COMPACTION_TOKENS`, `DEFAULT_CHECKPOINT_TOKENS`), and Codex also offers client-triggered `thread/compact/start {threadId}` (app-server schema `v2/ThreadCompactStartParams.json`). Estimate of the ceiling trade-off from measured data: compactions in this run happened at 167–229k (root); each recovery costs ≈45k uncached (mean of the 30 measured windows) plus the remote compaction call; a 150k ceiling lowers the average context from ~119k to roughly 85–95k (−20–28% cached tokens, ≈ −10–15% of cost) at ~+40% more compactions (+0.6M uncached ≈ +1%). A 100k ceiling would give −40% cached (≈ −20% cost) but doubles compactions and the risk of losing unrecorded reasoning; the checkpoint steer is the mitigation. Recommendation: 120–150k with the checkpoint at 90–110k; measure. Risk: medium.

**E3. Reasoning replay off for later responses in a call.** `pi-roles.ts:73–77, 590`; `SPEC.md:98` ("removes thinking blocks from every model input after the first response … the transcript retains them"); `README(solve):50`. → cached input. → Measured share here: replayed reasoning ≈ 11.5k of the 118.7k mean context (≈10% of cached tokens ≈ 5% of cost). → Does NOT transfer: Codex exposes no such option (no config key in the binary or schema). Only lever: lower reasoning effort where acceptable (E1), or shorter windows (E2). Risk: n/a.

**E4. Guidance frozen once per turn; consumed once; later advice waits.** `guidance.ts:90–141`, `docs/terms.md:80`. → no repeated re-reading of advice; no mid-turn churn. → Adaptation: audits and fresh-eyes reports enter only at a turn boundary via the digest (the YAML resume/continuation prompts already do this); the runner should not steer audit content mid-turn. Risk: none.

### F. Accounting and replay

Risk: none.

**F2. Idempotent resume: repeat `run` executes only the first missing call.** `workflow.ts:201–450`, `docs/role-runner.md:77,91`; `tests/efficiency.test.ts:190–236` (startup reuses derivation), `:326–393` (replay reads submissions once). → no duplicated model work after interruption. → Partially transfers: Codex `thread/resume` already reuses the conversation; the missing piece is at the record level — `unsaved-subagent-results.md` flush (in the diff) and the verify-once ledger (C1) make interrupted work reusable rather than redone. Risk: none.

**F3. Compact call summaries without reading attachments.** `SPEC.md:172`, `docs/role-runner.md:105`. → tooling cost, not model cost. → Adaptation: `records.py overview` is exactly this for the author; the UI's transcript views should show per-thread token meters rather than the model re-reading. Risk: none.

### G. Mechanisms that do not transfer (and why)

- **SQLite journal + fold that rebuilds phase from prompt bytes** (`workflow.ts:98–164`, `docs/role-runner.md:81`): the Codex app-server owns thread state; tcs-prover cannot reconstruct an author from a journal. Keep Codex's rollout; transfer only the *ledger* idea (C1, F2).
- **Zod-validated submission tools and the submission gate** (`roles.ts`, `SPEC.md:90`): the goal-mode author has no submit tool; `TurnStartParams.outputSchema` exists for controller-driven turns only (already used by `structured` nodes). Transfer as "PLAN paste at turn end" plus the runner validating that the final message contains a PLAN block.
- **`replayReasoning: false`** (E3): no Codex equivalent.
- **Per-role model profiles for subagents** (E1): not exposed for model-spawned subagents in this Codex build.
- **Pi's context estimator/reserve** (`SPEC.md:90`): Codex compacts server-side; the runner can only approximate with `tokenUsage` thresholds + `model_auto_compact_token_limit` / `thread/compact/start`.
- **Deterministic prompt = deterministic replay** (`docs/role-runner.md:81`): tcs-prover's author prompt is by design open-ended.
- **Reconstruction verifier** (C4): a strength mechanism that costs more; only opt-in.

## 3. The eight highest-value adaptations, ranked by (saving × adaptability) / risk

Savings are estimates on the measured profile under assumption A; they overlap and are not additive. A plausible combined outcome (P1+P2+P3+P5+P6) is total input ≈ 90–110M tokens instead of 268M and output −20%, i.e. roughly 35–45% of the current cost per active hour, which would also have kept the run inside the weekly quota.

1. **Single-task, bounded subagents; no inter-agent chat** (B2+B3). Saving ≈ 30–45% of run cost (subagents are 70% of input; 881 chat calls; 12.7 calls/result). Risk low–medium.
2. **Records-derived context: overview tool + section reads + read-once ledger** (A1+A2+A4). Saving ≈ 45% of uncached (node/AUDITS/INITIAL_PROMPT re-reads) plus it enables #3; ≈ 8–10% of cost alone. Risk low. Mostly landed; add the read ledger.
3. **Verify-once ledger and bounded verification briefs** (C1+C2+C3). Saving ≈ 15–25% of run input. Risk low–medium.
4. **Lower compaction ceiling with checkpoint, measured** (E2). Saving ≈ 10–20% of cost depending on ceiling; +1–2% recovery cost. Risk medium; run the pilot.
5. **Audit digest, PASS-free reports, auditors on a snapshot without pausing, capped at 25 min** (A3+E4+time). Saving ≈ 3% tokens, −18% wall time, and removes 1.17MB of full-report reads. Risk low. Digest landed; snapshot/no-pause remains.
6. **No narration, no INITIAL_PROMPT re-reads, batch reads** (B1+A5). Saving ≈ 6–10% of calls (141 standalone narration calls; 139 full cats). Risk none.
7. **Web-action budget enforced by the runner** (D1). Saving ≈ 5–8% (literature threads; 0.75MB results; 25 searches on one paper). Risk low–medium.
8. **Complete accounting: quota alarm/pacing + auditor usage capture** (F1). Saving: prevents the 100%-of-weekly-quota death and makes #1–#7 measurable; no direct token saving. Risk none.

Below the cut: per-turn effort for chores (E1; ≈ 5% of output, medium risk if misapplied); reconstruction tier (C4; cost up, strength up); reasoning-replay off (E3; not available in Codex).

## Proposals

- **[EFF-1] Single-task, bounded subagents that report once; no agent-to-agent chatter** (risk low; saving: 30-45% of run cost. Basis (measured): subagent threads = 188.9M of 267.9M input (70%); 881 inter-agent calls at ~120k avg context = ~105M cached tokens; assumption: a one-task subagent with a <=2KB brief and a call cap of ~25 (verification/chores) or ~40 (exploration) averages <=40k context and <=15 calls, cutting subagent input to ~50-70M and chatter to ~150 calls; price ratios per assumption A ($1.25/$0.125/$10 per M).)
  - mechanism: xean roles make one logical call each and communicate only through structured submissions at turn boundaries (pi-roles.ts:227-236 'Call submit_notes exactly once'; SPEC.md:88 stopAfterToolResult; guidance.ts:90-141 guidance frozen once per turn; submission gate maxResponses=4 pi-roles.ts:186-189,219-235). tcs-prover subagents were long-lived shared-workspace threads that exchanged 881 messages (600 SUB->ROOT, 281 ROOT->SUB), each a full-context model call on the sender, and cost 12.7 calls / 1.51M input tokens per result.
  - implementation: Prompt: workflows/author_critic.yaml SUBAGENT POLICY (already drafted in the working tree) plus two lines: 'Do not send progress or status messages to the root; the root does not poll subagents' and 'A subagent brief states its call budget; report once and stop'. Runner: workflow_runner.py goal_session message loop (the non-root branch near the `if not is_root(message): continue` check, ~line 1280 in the committed file; the diff already handles subagent compaction there): count thread/tokenUsage/updated per subagent thread and subAgentActivity kind=interacted; at the per-thread call cap or interaction cap send the existing steer helper with a 'finish and report' instruction; emit a status line with per-subagent calls and tokens.
